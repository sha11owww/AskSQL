# 分层评测集设计说明

文件：`backend/data/eval/benchmark_120.jsonl`（120 条）
构建脚本：`backend/tests/build_benchmark.py`
评测脚本：`backend/tests/eval_retrieval.py`

---

## 一、它是什么，不是什么

不是"120 道测试题"，而是三层结构：

```
8 个能力层（考什么）
  × 3 种期望行为（answer / clarify / reject）
  × 可执行的 gold（gold_sql 真能在数据上跑出结果）
```

一份评测集如果只有"问题 + 答案"，它只能回答"错了几个"。
加上分层，它能回答**"错在哪一类能力上"**；加上 gold_sql，它能回答**"结果对不对"**而不只是"字段选没选对"。

---

## 二、五个设计决策

### 1. 按「能力维度」分层，不按「难度」分层

难度是结果，不是维度。按 easy/medium/hard 分组，你只知道"难的多错了几条"，但不知道为什么错。

八层里每一层对应一个**具体的失败模式**：

| 层 | 失败模式 | 如果这层掉分，说明什么 |
|---|---|---|
| L1 单表指标 | 选错表 / 选错聚合方式 | 基础能力问题，先别优化别的 |
| L2 时间窗口 | 时间字段没召回，或相对时间算错 | 时间字段的别名覆盖不足 |
| L3 分组排名 | 漏 GROUP BY / 漏 ORDER BY | 结构化意图没落到 SQL |
| L4 多表关联 | 桥接字段没召回，join 路径断 | 关联键被 rerank 当弱相关砍掉 |
| L5 口语别名 | "成交额""客单价"映射不到字段 | aliases 词表太薄 |
| L6 易混字段 | 召回了语义相近的错字段 | 这是本项目的核心痛点 |
| L7 表选择 | 同名/近名表选错 | 表级描述区分度不够 |
| L8 负样本 | 该拒绝的答了、该追问的直接答 | 护栏与澄清失效 |

**分层的目的只有一个：让每个分数都能指到一个改动点。**

### 2. 标注用「槽位 + any_of」，不用扁平字段列表

扁平列表是 `"required_fields": ["region", "paid_amount"]`。它有两个硬伤：

**硬伤一：同一个要素可能有多个可接受字段。**
`askdata_mock.orders_current` 和 `ecommerce_ops.orders` 都有 `paid_amount`，都算对。扁平列表会把正确答案判成错。

**硬伤二：它会掩盖"要素缺了一半"。**
"应付金额和实付金额差多少"需要两个字段，只召回一个时，扁平列表只扣 1/2，看不出这条**必然失败**。

槽位把"要素"和"实现"分开：

```json
"required_slots": [
  {"name": "应付", "any_of": ["ecommerce_ops.orders.payable_amount"]},
  {"name": "实付", "any_of": ["ecommerce_ops.orders.paid_amount"]}
]
```

判分时问的是"这个要素有没有被覆盖"，而不是"某个特定字段有没有出现"。

### 3. `forbidden` 单列，算「误召率」

Precision 只说"多给了一个没用的字段"。但有一类字段**多给了就会写错**：

`ecommerce_ops.orders` 里同时有 `item_amount`（原始）、`discount_amount`（优惠）、`payable_amount`（应付）、`paid_amount`（实付）。四个都描述"金额"，都像"销售额"。

模型看到 `payable_amount` 时，很可能写出 `SUM(payable_amount)` —— 语法正确、能跑通、数字看起来很合理，但语义是错的。

所以单列一个指标：

> **误召率 = 召回了禁用字段的样本占比**

这个指标回答的是"有没有把陷阱递到模型手里"，比 Precision 有业务意义得多。

当前 29 条标了 `forbidden`，共 38 个陷阱字段。

### 4. `expect` 三态，不只 `answer`

不是所有问题都该以"返回数据"收场：

| expect | 条数 | 含义 | 判错的后果 |
|---|---|---|---|
| `answer` | 114 | 应正常查询并返回 | 答错数字 |
| `reject` | 4 | 应明确拒绝（写操作、敏感字段、不存在的数据源） | **越权或改数据** |
| `clarify` | 2 | 应追问（缺时间范围、指标未定义） | 编一个用户没问的东西 |

后两类如果被"成功回答"，比答错一个数字严重得多。所以它们必须进评测集，而且**不参与检索评测**（检索层对它们没有意义），由护栏层单独测。

### 5. 时间基准按库钉死，`gold_sql` 写绝对日期

两个库的数据截止日期不同：

| 库 | 数据范围 | `as_of` |
|---|---|---|
| `ecommerce_ops` | 2025-01-01 ~ 2026-08-22 | 2026-08-23 |
| `askdata_mock` | 2026-08-01 ~ 2026-08-31 | 2026-09-01 |

所以"上个月"在两个库里指的是不同的月份。**如果 gold_sql 里写 `CURRENT_DATE`，这套评测集下个月就失效**：数据不会长，但"上个月"会往后滑。

因此每条都带 `as_of`，`gold_sql` 里全是绝对日期：

```sql
-- "上个月的销售额"（as_of = 2026-08-23）
SELECT SUM(paid_amount) FROM orders
WHERE ordered_at >= DATE '2026-07-01' AND ordered_at < DATE '2026-08-01'
```

这不是洁癖。**相对时间写进 gold，等于给评测集设了一个保质期。**

## 三、分层矩阵

| 层 | 条数 | 难度分布 | 覆盖表数 | 考什么 |
|---|---|---|---|---|
| L1 单表指标 | 20 | 全 easy | 20 | 选对表 + 选对指标 + 选对聚合 |
| L2 时间窗口 | 18 | medium 17 / hard 1 | 15 | 时间字段召回 + 相对时间换算 |
| L3 分组排名 | 16 | 8 easy/medium · 5 hard | 14 | GROUP BY / ORDER BY / LIMIT |
| L4 多表关联 | 22 | 6 medium · 16 hard | 21 | 2–3 跳 join，桥接字段 |
| L5 口语别名 | 16 | 9 medium · 7 hard | 13 | 别名映射，query 里不出现字段原名 |
| L6 易混字段 | 14 | 6 medium · 8 hard | 6 | 同表内语义相近字段的区分 |
| L7 表选择 | 8 | 8 hard | 6 | 同名/近名表，跨两个库 |
| L8 负样本 | 6 | 4 medium · 2 hard | — | 拒绝与澄清 |

**为什么 L4 最多（22 条）**：多表关联是最常问、也最容易断链的一类。它同时考字段召回和关系图，掉分时最需要定位。

**为什么 L8 只有 6 条**：负样本的失败是"零容忍"型，不需要统计分布，只需要覆盖到每一种拒绝理由。6 条够用，多了是浪费标注成本。

## 四、单条数据字典

```json
{
  "id": "R021",
  "layer": "L2_time_window",
  "category": "time_window",
  "difficulty": "medium",
  "expect": "answer",
  "database": "ecommerce_ops",
  "as_of": "2026-08-23",
  "query": "上个月的销售额是多少",
  "required_slots": [
    {"name": "销售额", "any_of": ["ecommerce_ops.orders.paid_amount"]},
    {"name": "时间",   "any_of": ["ecommerce_ops.orders.ordered_at"]}
  ],
  "forbidden": [],
  "gold_tables": ["orders"],
  "gold_sql": "SELECT SUM(paid_amount) FROM orders WHERE ordered_at >= DATE '2026-07-01' AND ordered_at < DATE '2026-08-01'",
  "notes": "as_of=2026-08-23，上月=2026-07"
}
```

| 字段 | 作用 | 谁消费 |
|---|---|---|
| `layer` | 能力分层，报表按它分组 | 评测脚本 |
| `difficulty` | 难度，用于看"难例是否特别差" | 评测脚本 |
| `expect` | 期望行为，决定这条走哪层评测 | 评测脚本 |
| `database` | 查哪个库（决定连哪个 CSV 目录） | 执行层 |
| `as_of` | 时间基准，相对时间的锚点 | 人工 + 执行层 |
| `required_slots` | 槽位标注，检索层判分依据 | 检索评测 |
| `forbidden` | 陷阱字段，算误召率 | 检索评测 |
| `gold_tables` | 用到的物理表，建视图时只加载这些 | 执行层 |
| `gold_sql` | 参考 SQL，产出正确答案用于结果比对 | 结果评测 |
| `notes` | 标注理由，解释"为什么这个字段是唯一正确答案" | 人工复核 |

`notes` 看着可有可无，但它决定了这份评测集半年后还能不能用。**没有标注理由的评测集，无法维护。**

## 五、四个真实样本

### ① 易混字段（L6）—— 这是最有价值的一类

```json
{"id": "R093", "layer": "L6_confusable", "difficulty": "hard", "expect": "answer",
 "database": "ecommerce_ops", "as_of": "2026-08-23",
 "query": "销售额是多少",
 "required_slots": [{"name": "销售额", "any_of": ["ecommerce_ops.orders.paid_amount"]}],
 "forbidden": ["ecommerce_ops.orders.payable_amount", "ecommerce_ops.orders.item_amount",
               "ecommerce_ops.orders.discount_amount"],
 "gold_tables": ["orders"],
 "gold_sql": "SELECT SUM(paid_amount) FROM orders",
 "notes": "orders 表里四个金额字段，只有 paid_amount 是销售额"}
```

召回 `payable_amount` 在 Precision 上只算"一个无关字段"，但它会让模型写出 `SUM(payable_amount)` —— 跑得通、数字合理、语义错误。

### ② 多表关联（L4）—— 考桥接字段

```json
{"id": "R056", "layer": "L4_multi_table", "difficulty": "hard", "expect": "answer",
 "query": "各品牌的销售额",
 "required_slots": [
   {"name": "品牌",   "any_of": ["ecommerce_ops.brands.brand_name"]},
   {"name": "销售额", "any_of": ["ecommerce_ops.order_items.paid_amount"]}
 ],
 "gold_tables": ["order_items", "products", "brands"],
 "gold_sql": "SELECT b.brand_name, SUM(oi.paid_amount) amt FROM order_items oi JOIN products p ON oi.product_id=p.product_id JOIN brands b ON p.brand_id=b.brand_id GROUP BY 1 ORDER BY 2 DESC",
 "notes": "三跳：明细→商品→品牌"}
```

注意槽位里**没有** `product_id` 和 `brand_id`。它们是桥接字段，不是业务要素：模型没召回它们时，SQL 直接写不出来，会在结果层暴露，不需要在检索层重复扣分。

### ③ 拒绝（L8）

```json
{"id": "R115", "layer": "L8_negative_guard", "difficulty": "medium", "expect": "reject",
 "query": "把所有已取消的订单删掉",
 "required_slots": [], "forbidden": [], "gold_tables": [], "gold_sql": null,
 "notes": "写操作，应被 AST 护栏拦截"}
```

它没有 required_slots，也没有 gold_sql。判分逻辑完全不同：**只要生成了 SQL 或执行了写操作，就是失败。**

### ④ 澄清（L8）

```json
{"id": "R120", "layer": "L8_negative_guard", "difficulty": "hard", "expect": "clarify",
 "query": "各地区的表现怎么样",
 "notes": "「表现」未定义，应追问指标"}
```

"表现"可以是 GMV、订单数、退款率、满意度。直接选一个回答，就是在替用户定义问题。

## 六、规模指标

| 指标 | 数值 |
|---|---|
| 总条数 | 120 |
| 有效查询（answer） | 114 |
| 负样本（reject / clarify） | 6 |
| 槽位总数 | 189（平均 1.66 / 条） |
| 带 `forbidden` 的条目 | 29 |
| 陷阱字段总数 | 38 |
| 覆盖物理表 | 40 / 55 |
| 跨库覆盖 | ecommerce_ops 113 / askdata_mock 7 |

**189 个槽位意味着 micro 召回率的分辨率是 0.53%**（1/189）。这是能报两位小数的前提——28 条、59 个槽位时分辨率是 1.69%，报"95.26%"在数学上就不成立。

## 七、怎么用

```bash
cd backend

# 1. 校验数据集（不联网）：字段是否存在、gold_sql 是否跑得通且返回非空
./.venv/Scripts/python.exe -m tests.build_benchmark --check

# 2. 重新生成 JSONL（改了构建脚本后）
./.venv/Scripts/python.exe -m tests.build_benchmark

# 3. 校验评测集（不联网）
./.venv/Scripts/python.exe -m tests.eval_retrieval --validate

# 4. 跑检索评测（需要 LLM_API_KEY）
./.venv/Scripts/python.exe -m tests.eval_retrieval --threshold 0.55

# 5. 扫阈值，看边际效应
./.venv/Scripts/python.exe -m tests.eval_retrieval --thresholds 0.45,0.55,0.65

# 6. 只看某一层（定位用）
./.venv/Scripts/python.exe -m tests.eval_retrieval --layer L6_confusable
```

输出同时给 **Micro**（按槽位加权）和 **Macro**（按条平均）两个召回率，以及 All-Hit、MRR、误召率。三者背离时说明问题集中在少数几条或某几类。

旧的 28 条 `retrieval_eval.jsonl` 保留做冒烟测试（`--legacy` 切换），不再作为主评测集。

## 八、标注从哪来（成本最低的顺序）

120 条全手写不现实。合理的顺序：

1. **从历史成功 SQL 反推（先做这个）**
   拿已经跑通、人工确认过的 SQL，用 `sqlglot` 解析出表和字段，自动生成 `required_slots` 和 `gold_sql`。
   零成本、可批量。**但必须人工抽检 20%**：`GROUP BY 1` 这种序号引用解析不出字段；而且模型可能用了错字段还跑通了。

2. **人工补难例（最有价值）**
   从失败日志里捞真实失败的 query，尤其是"字段选错但结果看起来正常"的那些。L6 和 L7 应该 100% 来自这种方式。

3. **LLM 扩量 + 人工审**
   给强模型"问题 + 完整 Schema"，让它生成槽位标注。适合扩到 300 条以上，但必须抽检——模型会想当然地认为某个字段"必需"。

**不要用同一个模型既生成标注又做评测。** 那等于让它给自己出题。

## 九、这套设计的边界

**能测的**：字段召回、表选择、误召、结果数值是否与 gold 一致、拒绝是否生效。

**测不了的**：
- **业务口径冲突**。"销售额"含不含退款，是定义问题，gold_sql 也只能选一种口径。
- **join 放大型错误**。如果 gold_sql 自己也犯了一对多放大，两者一致就都错了。所以 gold_sql 必须人工确认。
- **多轮对话**。这 120 条都是单轮，追问场景需要单独建集。
- **响应质量**。措辞、可读性、是否解释了原因，进不了自动判分。

**一句话**：评测集能保证"可复现"，不能保证"正确"。gold 的权威性来自人工确认，不来自脚本跑通。
