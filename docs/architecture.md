# 架构说明

本文描述 AskSQL 的请求链路、关键数据结构与设计取舍。目标是让读代码的人先建立一张地图，
再去翻具体实现。

---

## 1. 总览

```
Vue 3 前端
    │  POST /api/query（SSE 流式）
    ▼
FastAPI（全部同步路由，交给线程池执行）
    │
    ▼
AskSQLService ── 组装上下文快照 ──► LangGraph 状态图
                                          │
                       ┌──────────────────┼──────────────────┐
                       ▼                  ▼                  ▼
                字段级混合检索      Schema 子图构建      受限 ReAct 查询
                       │                  │                  │
                       └──────────────────┴──────────────────┘
                                          ▼
                                   DuckDB（CSV 视图）
```

后端约 5.4k 行 Python，41 个模块。数据规模：55 张表、422 个字段、85 条表间关联、约 38 万行。

---

## 2. 请求全链路

状态图共 8 个节点，其中 `run_multi_database` 为预留位（当前返回「多库暂未启用」）。

```
START → preprocess
          ├─ direct_response → respond_directly → END
          ├─ data_qa         → answer_qa        → END
          └─ database_query  → retrieve_schema
                                  ├─ 需澄清 → human_clarification → retrieve_schema
                                  ├─ 单库   → prepare_single_database
                                  └─ 多库   → run_multi_database → END / 澄清
                                                 │
                                    clarification 为空 → execute_single_database
                                    clarification 非空 → human_clarification
                                                 │
                              execute_single_database ─┬─ needs_analysis → answer_qa → END
                                                       └─ 其余           → END
```

几个容易看漏的点：

- **意图是互斥三选一**，由一次模型调用同时产出 `action`、`standalone_query` 与抽取要素。
- **`human_clarification` 只有两个入口**：`retrieve_schema` 之后（检索判定信息不足）、
  `prepare_single_database` 之后（生成 SQL 前发现字段歧义）。前者实际很少触发，后者是主路径。
- **澄清走 `interrupt()` + `Command(resume=...)`**，从检查点恢复，不重新构建上下文。
- **`execute_single_database` 内部还有一层循环**：结果校验不通过时回灌重写 SQL，最多
  `VALIDATION_MAX_RETRIES` 次（默认 1）。这个循环在节点内，不体现在图拓扑上。

## 3. 检索层

### 3.1 为什么是字段级而不是表级

表级检索只能回答「该看哪几张表」，但生成 SQL 需要具体到字段。55 张表 / 422 字段的规模下，
字段级检索的召回质量仍然可接受，因此省掉了「表粗排 → 字段精排」的两阶段结构。

> 表数量上到千级、字段上到十万级时，这个决策必须反转：字段级 Embedding 会互相淹没，
> Rerank 按候选数计费的代价也不可接受。届时前置一层表级粗排，把候选压到几百个字段再精排。

### 3.2 字段文档

每个字段被序列化为一份文档，包含两类内容：

| 类别 | 字段 |
|---|---|
| 身份 | `doc_id`（形如 `ecommerce_ops.orders.paid_amount`）、库、表、字段名、中文名、类型 |
| 语义 | 描述、角色（指标 / 维度 / 时间 / 键）、别名、样例值、画像（基数、空值率、取值范围） |

为了让不同的检索器看到各自适合的文本，同一份字段会派生**三路文本**：

- `keyword_text`：字段名 + 中文名 + 别名，供 BM25 做词面匹配
- `semantic_text`：描述 + 业务语义，供向量检索
- `rerank_text`：完整语义片段，供交叉编码器精排

### 3.3 召回与融合

```
BM25（中文 bigram，k1=1.5, b=0.75）  top 30 ┐
                                            ├─ RRF 融合（1/(60+rank)）top 40 ─ Rerank 精排
Dense（1024 维，余弦）               top 30 ┘                                        │
                                                                    阈值 0.55 过滤 ──┴─ 取前 20
```

参数全部可通过环境变量调整（`BM25_TOP_K` / `DENSE_TOP_K` / `RRF_TOP_K` /
`SCHEMA_RECALL_THRESHOLD` / `MAX_SCHEMA_FIELDS`）。

低于阈值的命中不会直接丢弃，而是放进 `low_confidence_candidates` 一并交给模型，
由模型判断是否需要 —— 阈值是召回的下限，不是唯一真相。

### 3.4 索引持久化

索引以 JSON 形式存于 `backend/data/schema_store.json`，向量内联存储，启动时全量载入内存。
文件带签名（Schema + 关联关系的哈希），签名不匹配即自动重建。

> 这是「单机、小规模、零外部依赖」的取舍。生产环境应当把关系库作为事实源，
> 向量库与全文索引只作派生索引，并按 `content_hash` 做增量更新。

## 4. Schema 子图

检索给出的是**一组散落的字段**，它们可能分布在多张表上、彼此之间没有直接关联。
直接把字段列表塞给模型，模型只能猜表怎么连。

构图做三件事：

1. **定位表集合**：命中字段所属的表。
2. **补桥接字段**：以字典序第一张表为锚点，在 85 条预定义关联上做 BFS 最短路，
   把路径上的关联字段补进来（标记 `source="relation_key"`，打分记 1.0）。
3. **文本化**：按表分组输出为可读文本，含表名、中文名、字段清单、字段类型与表间关联说明。

输出结构只有 6 个顶层键：`database` / `databases` / `graph_version` / `tables` / `fields` / `joins`。
字段从命中时的 28 个键瘦身到 11 个，只保留模型真正需要的部分。

> **这套机制不参与召回。** 向量检索决定「看哪些字段」，图决定「这些字段怎么连」。
> 两者串联，不是二选一。

已知风险：如果某张表与其他表没有任何关联，它仍会留在图里但没有任何边。
模型可能据此猜测关联，或退化为笛卡尔积。当前仅靠提示词约束，未做显式标注。

## 5. 生成与执行

### 5.1 受限 ReAct

查询 Agent 不是自由循环，而是有明确边界的工具调用：

- 可用工具由权限动态决定：用户能访问哪些库，才注册对应的 `query_{database}`
- 每轮只允许一次工具调用，最多 `MCP_MAX_TOOL_CALLS`（默认 3）轮
- 工具以 MCP 协议暴露，标注 `readOnlyHint`，随进程内注册

### 5.2 SQL 护栏

在执行前对 SQL 做 AST 级校验（`sqlglot`）：

- 只允许单条 `SELECT` 或 `WITH` 语句
- 拒绝所有写操作与 DDL
- 拒绝 `SELECT *`（必须显式列出字段，便于结果校验与权限核对）

这是一层**结构性**防护，不依赖模型遵守提示词。

### 5.3 执行

DuckDB 对 CSV 建视图后执行，结果取前 200 行（多取 1 行用于探测截断），
日期与 `Decimal` 归一化为 JSON 友好类型。

执行失败**不抛异常**，而是返回带 `error` 的失败对象 —— 这是自纠错能够工作的前提：
上层拿到的是数据，可以决定「回灌重写」还是「直接失败」。

## 6. 三层校验

SQL 跑通不等于答案正确。三层验证依次收紧：

| 层 | 输入 | 判断 | 失配时 |
|---|---|---|---|
| 意图规则比对 | 预处理抽取的指标 / 维度 / 操作 vs SQL 与结果列 | 纯规则，零模型调用 | 触发重写 |
| 模型自评 | 原问题 + SQL + 列名 + 前 50 行 + Schema | `{valid, retryable, reason}` | `retryable` 为真则重写 |
| 重写 | 上一版 SQL + 失败原因 + 列 + 样例行 | 重新走生成与执行 | 超出次数则保留数据并提示 |

设计上有两条克制：

- **规则层只做触发器，不做终审**。规则是启发式的，会误判；让规则单独把结果判成失败，
  用户会拿到「校验未通过」却看不到可能正确的数据。
- **重写只重跑「生成 → 执行 → 校验」**，不回退检索。检索在相同输入下是确定性的，
  重跑只会拿回同一批字段；真正需要回退的是「抽取漏词」这类上游问题，那属于重建整条链路。

重写次数到顶后，结果状态仍是 `completed`，数据保留，只在说明里追加疑点。

## 7. 会话与记忆

三层，从重到轻：

| 层 | 载体 | 内容 | 是否进上下文 |
|---|---|---|---|
| 归档 | SQLite | 完整 `QueryResult`（含全部行） | 否，按需读取 |
| 短期记忆 | 进程内 | 上一版摘要 + 未摘要轮次的完整文本 | 是 |
| 路由上下文 | 进程内 | 最近 6 轮的轻量元数据 | 是，仅用于意图判断 |

**短期记忆里永远不含数据行**，只保留列名与行数。完整数据通过「最近结果」和「参考表」两条通道按需传递 ——
这是上下文不被表格撑爆的关键：成本从「每轮都传整张表」变为「只在分析时传一次」。

摘要按 token 触发（阈值 12000，批次 6000，保护最近 5 轮）。摘要失败不标记轮次，
原文继续进入上下文：宁可多花 token，不可丢信息。

## 8. 安全

三层纵深，逐层收紧：

1. **检索层**：按用户权限过滤字段，无权访问的字段不会进入候选，更不会进入图
2. **工具层**：只注册用户有权限的库对应的查询工具
3. **执行层**：AST 护栏限制语句形态

越权访问是唯一**不允许降级处理**的错误类型 —— 其他失败都能重试或降级，
授权失败必须直接终止，否则「跳过这个字段」本身就泄露了它的存在。

## 9. 设计取舍

按「为什么不做」记录，避免后来者重复讨论。

### 9.1 重试留在节点内，不上升到图

判据：**是否需要挂起等待外部输入**。澄清需要，重写不需要，所以只有澄清在图上有节点。

好处是图拓扑稳定、检查点语义不变；代价是执行轨迹在图上只出现一次，
看不出内部转了几圈（只能从执行日志的 `attempt` 字段读）。

### 9.2 只做单轮复合分析，不做任务规划

当前支持「先查数、再分析」这一种复合形态，流程在编译期固定。

真正的多步依赖（「先查 A，看结果再决定查不查 B」）需要运行时生成任务列表，
代价是图从 DAG 变成任务执行器：澄清语义、检查点语义、失败回滚都要重新设计，
且路径不可预测、排查困难。在单库为主、多数需求能压成一条 SQL 的场景下，收益不抵成本。

### 9.3 分析只看 50 行样本

模型拿到的是有损压缩后的样本，因此四类事情它本质上做不了：精确聚合、跨行排序找极值、
判断分布尾部、还原 join 放大后的口径。

正确的分工是：**聚合、排序、过滤全部下推给 SQL，模型只解释已经算好的数字和样本呈现的形态。**

### 9.4 已知缺口

| 缺口 | 影响 | 处理方向 |
|---|---|---|
| 多库查询未实现 | 跨库请求直接失败 | Handoff：按库分组并发查询 + 结果合并，合并语义需显式声明 |
| 重试次数各自计数 | 最坏情况 2×3×3 = 18 次请求叠加 | 引入贯穿全链路的截止时间预算，用时间兜底而非次数 |
| 错误分类粗糙 | 表不存在与字段写错同样处理，导致空转重写 | 按错误文本分类：`Catalog Error` 回检索，`Binder Error` 才重写 |
| 空结果无探针 | 无法区分「业务为 0」与「过滤过头」 | 跑一条放宽条件的计数 SQL 做三态判定 |
| 复现错误无检测 | 模型可能连续多轮输出相同 SQL | 对 SQL 与错误文本取签名，重复即提前跳出 |
| 孤岛表无标注 | 模型可能猜测关联 | 在文本化时显式标注「本表无已知关联」 |
| 路由靠提示词 | 复合请求可能被判成纯分析，直接跳过查询 | 拆成两个独立布尔（需查询 / 需分析），并加「无历史数据时不可能走分析」的硬约束 |

## 10. 目录结构

```
backend/
  app/
    api/routes.py               HTTP 接口（登录、查询、会话、配置）
    workflows/
      query_graph.py            状态图定义与全部节点实现
      state.py                  图状态结构
      result_builder.py         结果对象组装（成功 / 失败 / 串联分析）
    retrieval/
      service.py                混合检索与融合排序
      graph.py                  Schema 子图构建
      store.py                  索引持久化
    querying/
      single_database_agent.py  受限 ReAct 查询循环
      data_qa_agent.py          数据分析 Agent
      duckdb_engine.py          SQL 执行
      response_generator.py     结果校验与文案生成
      intent_check.py           意图与结果结构的规则比对
    mcp_runtime/                进程内 MCP 服务与工具注册
    services/                   上下文、短期/长期记忆、会话归档
    security/                   鉴权与字段级访问控制
    skills/                     Markdown 技能提示词
  data/
    databases/                  合成数据集（CSV）
    eval/                       评测集
  scripts/                      数据与 Schema 生成脚本
  tests/                        单元测试与评测脚本

frontend/
  src/
    App.vue                     主界面
    api.ts                      接口封装与 SSE 解析
    components/                 结果表格、图表、报告卡片
```

## 11. 本地调试

```bash
# 全量单元测试
cd backend && ./.venv/Scripts/python.exe -m unittest discover -s tests

# 校验评测集的字段引用与 gold_sql 可执行性（不联网）
./.venv/Scripts/python.exe -m tests.build_benchmark --check

# 检索层评测（需要 Embedding / Rerank Key）
./.venv/Scripts/python.exe -m tests.eval_retrieval --thresholds 0.45,0.55,0.65

# 数据连通性检查
./.venv/Scripts/python.exe -m tests.connectivity_check
```

运行期开关集中在 `backend/.env`，全部默认值见 `backend/.env.example`。
`GET /api/config` 会返回当前生效的运行参数（不含密钥）。
